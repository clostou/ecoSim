## 2. ndarray

ndarray应当管理底层内存的创建与释放。

处理结果：已采纳。该要求已在当前实现和`ndarray-design.md`中落实，`ndarray<T, Rank>`作为拥有数据的主容器负责底层内存生命周期管理。

## 3. 索引

支持负数索引和省略号索引（性能开销大或显著增加接口复杂性的话就算了）

处理结果：部分采纳。

1. 负数索引：已采纳，纳入固定秩首版计划。
2. 省略号索引：暂缓。虽然基于固定秩和参数个数可以做静态展开，但会显著增加索引系统的模板复杂度和首版实现成本，因此延期到后续版本再评估。该延期已同步到`ndarray-design.md`。

## 4. 性能

再次强调极值性能优化，能放到编译期的完成的计算就尽量编译期完成。

处理结果：已采纳。设计文档已进一步收紧接口策略：凡是可能改变秩的主接口，优先使用模板参数表达目标秩、轴编号和置换顺序；对会让返回类型依赖运行时标志或字符串解析结果的接口（如无参`squeeze()`、通用字符串`einsum`）则延期到动态秩接口层。

## 5. einsum编译期解析

新请求：`einsum`未来可能作为神经网络计算的主力接口之一，希望评估是否可以将表达式解析放到编译期完成，并据此规划方案。

处理结果：建议采纳为未来高优先级方向，但不纳入当前 M1~M5 的首版必须交付范围。

### 5.1 结论摘要

1. 可行，业界确有类似做法，尤其适合固定秩、固定表达式的张量计算场景。
2. 对本项目而言，编译期解析与固定秩设计是天然契合的，因为输出秩、轴映射和很多快路径都可以在编译期推导。
3. 推荐路线不是“一上来只做运行时字符串 parser”，而是优先规划编译期前端，再在后续补运行时 facade。

### 5.2 预期收益

1. 消除运行时表达式解析与标签映射开销。
2. 在编译期生成输入轴映射、输出轴映射、归约轴集合和置换信息。
3. 更早命中 `transpose`、`dot`、`matmul`、`batched_matmul`、`outer`、`trace` 等快路径。
4. 更符合“能放到编译期就尽量放到编译期”的性能目标。

### 5.3 主要代价

1. 编译时间会增加。
2. 模板错误信息会更复杂。
3. 如果继续保持 C++17 基线，表达式写法会不够优雅，通常需要类型级字符包或宏包装。
4. 若追求完整 NumPy 风格语法，constexpr parser 的实现复杂度会显著上升。

### 5.4 推荐方案

建议采用双层方案：

1. 固定秩核心层继续先实现 `dot`、`matmul`、`batched_matmul`、`outer`、`trace` 等静态收缩算子。
2. 在后续版本中增加编译期 `einsum` 前端，用于固定表达式热路径。
3. 运行时字符串 `einsum` facade 继续延期到动态秩接口层或外层便捷接口。

### 5.5 语言标准建议

1. 若坚持 C++17：编译期解析仍然可做，但更适合用类型级字符包、用户自定义字面量模板或宏包装，接口美观性较差。
2. 若允许局部提升到 C++20：可以基于 `fixed_string` 一类类 NTTP 提供更自然的 `einsum_ct<Expr>(...)` 前端，工程可维护性更好。

### 5.6 建议的阶段路线

1. 当前阶段：保持 `einsum` 核心能力由静态算子承载。
2. 后续阶段一：实现“显式输入标签 + 显式输出标签”的编译期 `einsum` 前端，只覆盖当前设计文档里的核心子集。
3. 后续阶段二：如确有需求，再增加运行时字符串 facade，并把常见模式分发到静态算子或编译期前端。

## 6. attention风格einsum的固定秩通用实现

新请求：观察神经网络原型中类似 `qkein, kejn -> qkijn` 这类 `einsum` 模式，讨论在不依赖传统简单快路径的情况下，是否存在更优化的固定秩通用实现。

处理结果：建议采纳，作为 `einsum` 设计的关键实现方向之一，并已同步到`ndarray-design.md`。

### 6.1 观察结论

当前神经网络原型中的 `einsum` 主要不是任意多输入、任意标签组合的通用场景，而是：

1. 二元张量收缩。
2. 一元 reduce。
3. 无归约的 batched outer 或带轴扩展的逐元素乘法。

因此，比起做一个“运行时 parser + 任意递归循环”的通用解释器，更合理的方向是做一个固定秩的通用 contraction 引擎。

### 6.2 推荐方案

推荐把固定秩通用实现拆成两个主内核：

1. `contract<LhsLabels, RhsLabels, OutLabels>(lhs, rhs)`
2. `reduce_labels<InLabels, OutLabels>(x)`

其核心思想是将二元 `einsum` 统一降成如下规范形：

1. `B`：batch 轴
2. `M`：左输入自由轴
3. `N`：右输入自由轴
4. `K`：归约轴

然后把问题转换为 `[B][M][K] x [B][K][N] -> [B][M][N]` 的 batched contraction 内核。

### 6.3 为什么比“permute + multiply + sum”更优

1. 避免显式构造中间乘积张量。
2. 能把乘法和归约融合到同一个 kernel 中。
3. 更利于缓存利用、blocked loops 与向量化。
4. 更适合固定秩设计下的编译期轴分类与静态调度。

### 6.4 对当前神经网络用例的适配性

对于 `qkein, kejn -> qkijn` 这一类模式，虽然表面上不像传统矩阵乘，但经过轴分类与折叠后，本质上仍然可以归入 batched contraction family，因此并非“完全用不上快路径”，而是需要一个比传统 matmul 更泛化的 contraction 快路径。

### 6.5 需要额外特化的热点

并非所有 `einsum` 都应原样走通用 contraction。像 softmax backward 中显式构造 Jacobian 的写法，会产生高阶中间张量，内存代价很高。对此更推荐使用代数融合公式，直接实现 Jacobian-vector product，而不是把中间 Jacobian 物化出来。

### 6.6 当前建议

1. `einsum` 固定秩实现的主方向应从“字符串 parser”转向“标签驱动的 contraction 内核”。
2. 通用固定秩 contraction 内核应成为 M5 的核心。
3. attention / softmax backward 等高频模式可在通用 contraction 之上继续做融合特化。
